## Review questions

### 1. Signal: can `data/published.json` disagree with the files in a real dev flow?

- Both files are tracked. Each commit is consistent, because `buildSnapshotAssets` fails when a published university has no list (`lib/snapshot-manifest.ts:75`).
- The crawler never deletes `programs.json`. It writes it with `atomicWrite` (`catalog-service/roadmaps.ts:138`). I found no reset path that removes it.
- `npm run dev` is `next dev` (Node, with a filesystem). So the new branch runs in dev. In the Worker, `data/published.json` is not in the snapshot manifest, so `isPublished` gives `false` there. The Worker always has the list of a published university, so this is correct.
- `isPublished` matches `"<id>/"` as a prefix (`lib/roadmap-reader.ts:130`). `northeastern-x/...` does not match `northeastern`. Correct.
- Disagreement happens only when a person deletes the file or edits `published.json` by hand. In both cases "missing" is the true text.

Result: the signal is sound.

### 2. Blast radius: one lost file makes the whole list 404

- `listRoadmapUniversities` uses `Promise.all` (`lib/roadmap-reader.ts:158-166`). One throw fails the whole list. So yes: one lost file hides every university.
- This is not a new failure model. Before this change, an invalid `programs.json` already failed the whole list (generic 503).
- Today there is only one crawlable university. Before this change, a lost northeastern list gave 200 and the selector was hidden (no selectable university). Now the selector shows "Unable to load universities: The program list (programs.json) is missing." That is the true text that the issue asks for.
- The state is dev-only. The build blocks it in production.

Result: acceptable for this ticket. Not a regression in production. See M1 and L1 for the remaining gaps.

### 3. Worker CPU on the hot path

- `isPublished` runs only when a crawlable university has no list. No such university exists today.
- In production, `handleRoadmapsRequest` keeps each body per key (`app/api/roadmaps/route.ts:61-64`). So the extra read runs at most once per key per isolate.
- On the Worker, the read is one `stat` (ENOENT) plus one lookup in the memoized manifest. The same cost already exists for the `programs.json` read.

Result: no hot-path cost.

### 4. `lib/snapshot-assets.ts` change in production

- `response.json().catch(...)` changes only the rejected case. A valid JSON body resolves with the same value. The `memo` and `forget` logic is unchanged.
- The change is needed in `vite dev` (workerd): if the dev module fails, `env.ASSETS` serves HTML, and `response.json()` gives a `SyntaxError`. Without the wrap, that error reads as `invalid-programs`. With the wrap, it is the generic 503. Correct.
- No test reaches this code (L2).

Result: correct by inspection. Safe for a valid asset.

### 5. Build pass-through

- `lib/snapshot-manifest.ts:75` passes `invalid-programs` through with no "Published snapshot" prefix. The new test fails without it (1 fail above). Correct, and it follows the #136 architecture note.

### 6. Tests fail without the change
