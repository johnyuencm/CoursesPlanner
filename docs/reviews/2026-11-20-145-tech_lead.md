## Focus areas from the brief

1. **Focus management.** Correct on the planner.
   - Focus moves before `reloadCatalog()`, so it never drops to `body` when the button unmounts (`catalog-state.tsx:16-22`).
   - `tabIndex = -1` keeps the `h1` out of the Tab order. There is no focus trap: the next Tab goes to Try again (record line 113).
   - React reuses the `h1` node when the board lands. `PageHeading` is slot 0 of both fragments (`planner-board.tsx:250` and `:310`). So focus survives success. The record confirms "Focus when the board lands: h1".
   - The ring shows only for the keyboard. The only rule is `:focus-visible` (`globals.css:81`). A mouse press gives no ring (record line 118).
2. **`role="alert"` once.** Correct. The alert element mounts with its text in one commit. Later re-renders do not change its text, so screen readers do not speak it again. A second failure mounts a new element, and that announcement is wanted. The server HTML is the loading branch, so no alert is in the prerender. Real screen reader output is not checked (record, "Not checked").
3. **15rem vs #144's 100vh.** No conflict. The 15rem rule is on the child (`.board-placeholder > .empty-state`). The 100vh is still on the wrapper. `.board-failed` has no `min-height`, so the #144 test "the failure state reserves no blank screen" still holds (`planner-page.test.ts`). Board-land CLS is unchanged (record: 0.027 / 0.004 / 0.024 / 0.004).
4. **Fake DOM test strength.** The test runs the real `AppProvider` and `PlannerBoard` through React's client renderer and event delegation. It is falsifiable: without the focus move, the button unmounts and `activeElement` becomes `body`. It also fails on any unexpected `console.error`, which catches `act` warnings. Gaps are in L1.
5. **Small-phone regression.** Real and documented (M2).
6. **Worker CPU.** No risk. All changes are client render paths. The planner pages are prerendered (record: 387 routes). The server HTML changes by one short line and a moved panel. No new server work.

## Findings

### Medium

**M1. The focus move lives in the shared component, but it is a silent no-op where no `main h1` exists.**
- `components/catalog-state.tsx:18` runs `document.querySelector("main h1")` for every non-quiet and quiet failure card.
- On Explore (`course-graph.tsx:686`, no `PageHeading` while `!catalog`) and Courses (`courses-explorer.tsx:75`), it finds nothing. Focus still drops to `body` there.
- The code comment at `catalog-state.tsx:17` says "The page heading stays", which is false on those two pages. There is no `shortcut:` comment for the limit.
- The record states this limit (judgment call 3). It is not a regression: the base also dropped focus to `body`. But a reader of the shared component gets a wrong contract.
- Also: the selector picks the first `main h1` in document order. That is correct today, because `PageHeading` is the only `h1` source (`ui.tsx:8`). It is a coupling to page structure, not to the component.

**M2. While the catalog loads, the backup buttons are below the fold on 360x640 and 375x667.**
- `planner-board.tsx:257` moves `PlanBackup` inside the placeholder, under the 15rem loading card.
- Record: Download backup is at y 586-630, under the bottom bar (576 / 603). On the base it was visible at y 334-378.
- The heading still says "Your local plan remains available for backup while the catalog loads." (`planner-board.tsx:251`). The text points at controls that the user cannot see on those phones.
- The trade-off is real and honest (record judgment call 5: the other layout gives CLS 0.235 at the failure). No data is lost: the buttons are one scroll away. I rate it medium because a slow load on a small phone is the case where the backup matters most. PM should accept or reject the trade.

### Low

**L1. The focus test has gaps.**
- `tests/fake-dom.ts:74-76`: `focus()` accepts any `tabindex`. If the code set `tabIndex = 0`, the test still passes, and the `h1` would enter the Tab order. No test checks the `-1` value.
- The success path (board lands, focus stays on `h1`) is not tested. The fake DOM cannot render the loaded board (its own `shortcut:` comment). The record checks it live only.
- `fake-dom.ts` is 135 lines of test code that we must keep. It is marked `shortcut:` with an upgrade path (jsdom). That is acceptable.

**L2. Failure CLS at 1280 rose from 0.065-0.072 to 0.084.** It is still under 0.1. The record names the sources (static page text comes into view, buttons move from right to left). The `shortcut:` at `planner-board.tsx:256` and `globals.css:569` depend on copy line counts at 360-1280 px. A copy change can break CLS with no test to catch it.

**L3. `role="alert"` on a container that holds a button.** `ui.tsx:60` puts the alert on the whole card, so the announcement also reads "Try again, button". This works, but ARIA intends `alert` for non-interactive content. Not a blocker.

**L4. `tabindex="-1"` stays on the `h1` after the first retry.** A mouse click on the heading text then focuses it. No ring shows (`:focus-visible` only), so the effect is small. React does not own the attribute, so it will not fight a re-render.
