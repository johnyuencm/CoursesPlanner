## Focus questions

```text
first load:   heading + backup | placeholder >= 100vh (status at top) | page text (below fold)
board lands:  heading + backup | board (taller than 1 screen)         | page text (further down, out of view)
failure:      heading + backup | failure state (220 px)               | page text (moves up, 0.031-0.072)
```

1. **`100vh` on mobile.** `100vh` is the large viewport (toolbar hidden). It is never smaller than the visible area. The page text top is the heading height plus `100vh`, so it is below the fold with the toolbar shown or hidden. `100dvh` would resize while the toolbar moves, and that can itself move content. `100svh` would also work, but gives less margin. `100vh` is the right choice. See L1 for the test gap.
2. **Short or empty plans.** When the board is shorter than the placeholder, the page text moves up into view. The record measures this case: no terms at 2560x1440 gives 0.018. Tall portrait screens (for example 1440x2560) are not measured. See L2.
3. **Screen readers and focus.** The placeholder `div` has no role, no text and no `tabindex`. Assistive technology skips it. `role="status"` is its first child, so the status still speaks once. Tab order does not change. No finding.
4. **Print.** `globals.css` has no `@media print` rules. A print during the load gives one blank screen height. The window is about 2.5 s and the board is not printable then. No finding.
5. **Does the test pin the behaviour.** It pins the structure: the status is inside `div.board-placeholder` while loading, and the failure state has no placeholder. It pins the CSS value with a text regex. It does not measure CLS or the page text position. See L3.

## Findings

### L1 (low): no check on a real mobile browser with a dynamic toolbar

- Where: `app/globals.css:567`; record, "Method" step 2.
- The 390x844 runs use Playwright emulation. Emulation has no browser toolbar, so `100vh` equals the visible height there. The argument in focus question 1 holds by the CSS spec, but no run shows it.
- Risk: low. A larger placeholder only keeps the page text further below the fold.

### L2 (low): tall portrait screens are not measured

- Where: record, table "Other viewports and plans".
- The worst case is a short board (no terms) on a tall screen. The tallest measured screen is 1440 px high. A 2560 px high screen can show the page text in the first screen and then move it when the board lands.
- Risk: low. The 2560x1440 no-terms case gives 0.018. CLS scales with the moved area, and the move is up, by the height difference only.

### L3 (low): the test pins the CSS text, not the outcome

- Where: `tests/planner-page.test.ts:147`.
- The regex needs the exact text `.board-placeholder { min-height: 100vh; }`. A correct change, for example to `100svh` or a `max()` form, fails the test. A regression elsewhere, for example a new element between the placeholder and the page text, or a board that becomes shorter than one screen, passes the test.
- The repo has no browser test runner (`package.json` `test` runs `tsx --test` only). So the CLS outcome lives only in the manual record. The red runs in the record show that the test does fail before the fix and with `220px`. It is not a false green.
- Risk: low. The guard is weak but honest.
