### Focus points

- **Stale or wrong data.** The memo lives for one isolate. A deploy gives new isolates and a new asset set. The `ASSETS` binding belongs to the same Worker version. I found no path that serves old data.
- **Failure handling.** `memo()` in `lib/snapshot-assets.ts` forgets a rejected fetch, so the next request tries again. `readCatalog()` writes its cache only on success. `worker.ts` forgets a failed slug `Set` and sends the request to vinext unchanged. No failure stays in memory.
- **Concurrent first requests.** Each caller sets the shared promise synchronously after its `await`, so only one fetch goes out for each file.
- **Path traversal.** The reader fetches only paths that the manifest lists (`Set.has`). Ids pass `validId` before path joins.
- **Public files.** Only `data/catalog.json`, the filtered `programs.json`, the published roadmap and `catalog-service/universities.json` ship. No `data/raw/`, no `.roadmap-crawl-status.json`, no tokens.
- **CPU.** The Worker no longer validates snapshots at request time. The first `/courses/*` request of an isolate now fetches and parses `data/catalog.json`. `JSON.parse` of this file takes about 0.3 ms in Node. The API routes still keep the serialized body (`readCatalog()` gives the same object, so the identity check holds).
- **Unpublish and CLI.** The tests cover both. The build filters `programs.json` to the allowlist.
- **Docs.** `README.md` and `docs/deploy.md` agree with the code, except finding 1.
