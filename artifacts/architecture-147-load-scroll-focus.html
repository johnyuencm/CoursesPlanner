Strong in-process serves #147: focus to build in this pass

After: focus moves before paint

sequenceDiagram
  participant R as Render
  participant C as Commit
  participant B as Browser paint
  R->>R: focus is in the loading wrapper, so keepFocus is true
  C->>C: remove the old panel, focus goes to body

  C->>C: layout effect, Download backup takes focus, no scroll
  C-->>B: the first frame paints with focus on Download backup

Problem: The hand-off reads focus in the render, but it moves focus in a passive effect (useEffect). A passive effect can run after the browser paints. Live, the gap is 12 to 17 ms, and 1 of 6 Tab runs painted one frame with focus on body (TL-L1, UA-L2). The test cannot see the gap, because act() runs both kinds of effect before the assert.

Solution: Move focus in a layout effect (useLayoutEffect). React runs it in the same commit that removes the old panel, so the browser cannot paint between the two. A probe after the board reads focus in its own layout effect: that is the focus of the first frame that can paint.

Interface: The hand-off promises "focus stays on Download backup when the board lands". That promise includes an order: it must be true when the board first paints. Today the module meets it only at the end.

  • Locality: the promise holds in every frame.
  • The test pins the order, not only the end state.
  • One word of product code.
  • Known pattern: graph-canvas.tsx:126 uses useLayoutEffect.

Risk: focus() in a layout effect can make the browser do style and layout inside the commit. The browser does this layout before the paint anyway. The live check below measures CLS and the place of the page text again.
