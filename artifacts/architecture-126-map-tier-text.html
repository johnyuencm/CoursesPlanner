Problem (reviewers): PM L1 and two TL lows say that the tier is computed in three places.

Analysis: All callers use one deep module, requirementTier, with the same catalog. So they cannot disagree. The toast reads the catalog, not progress. Then its callback depends only on catalog, and the context value keeps its identity (CR8). The page calls run at build time (prerendered).

6. The test reaches past the provider interface

Speculative

Files: components/app-provider.tsx:100 (export const AppContext), tests/planner-page.test.ts (LoadedPlanner).

Problem: The provider loads the catalog in an effect, so a server render has no catalog. The test exports the raw context and builds progress the same way as the provider. If the provider changes how it builds progress, the test does not follow.

Solution: The provider accepts a catalog. Two adapters would justify that seam: the network fetch in the app and a given catalog in tests.

Why not: The test also sets the picker and target state, so the context export stays. A prerender seed puts the whole catalog into the page payload. #140 owns the loading-state decision.
