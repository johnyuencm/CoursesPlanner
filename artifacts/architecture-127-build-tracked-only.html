Problem: The crawler module wrote the status file, but the shared reader module read it. So in dev, the app's list and ?university= answers depended on ignored crawler state. The Worker never has that file.

Solution: readProgramDirectory() builds the directory from programs.json only, as the Worker did. readState() moves beside its writer, persist(). The operator views pass readCrawlDirectory to listRoadmapUniversities(), so their output does not change.

Deletion test: Delete readState() from the shared reader. The status read joins the status write (locality). The app needs nothing new. The complexity concentrates.

  • Dev answers like the Worker.
  • Locality: status read and write in one module.
  • Two adapters justify the seam: tracked status for the app, persisted status for the operator.
  • The three app endpoints agree (PM medium, UA low-2).
  • Stale crawl output cannot hide the selector (UA low-1).
  • The Worker bundle no longer names the status file (0 files in dist/server).

2. One error vocabulary for roadmap reads

Worth exploring in-process not built: not #127

Files: lib/roadmap-reader.ts (throw sites), app/api/roadmaps/route.ts (safeReadError), catalog-service/server.ts (prefix match), catalog-service/cli.ts.

  M -->|response| N["route.ts"]
  M -->|response| V["server.ts"]
  R -->|message| L["cli.ts"]

Problem: The reader's error interface is message text. Two transports match message prefixes. A new error kind needs edits in three files.

Solution: The reader throws one small error type with a kind. One map gives the HTTP status, the public text and the log line.

  • The UA low-2 text ("no program list" instead of "Unknown roadmap program.") becomes a one-line change.
  • The catalog service also logs the cause of its 503. Today it does not.

Why not now: It does not change which files the app reads. Do it with the next new error kind.

3. One checked program-list read per build and per isolate

Speculative

Files: lib/roadmap-reader.ts (readPrograms), lib/snapshot-manifest.ts, lib/snapshot-assets.ts.

Problem: The build reads and checks programs.json 6 times for 5 published keys. On the Worker, readPrograms() checks the file again and sorts the memoized asset object in place (TL low-3: the sort is idempotent, so no bug). docs/deploy.md says the Worker does not check the files again. That is true for the program pages, not for /api/roadmaps.

Why not: The build cost is small. The route memo already keeps one 200 body per query. A memo in Node dev would serve stale files. Revisit if /api/roadmaps nears the 10 ms CPU limit.

4. Dev can serve a roadmap that is not published

Speculative

Files: lib/roadmap-reader.ts (readReadyRoadmap), data/published.json.

Problem: After a local crawl, dev serves any ready roadmap on disk. The Worker serves only the published ones. Today the tracked programs.json lists exactly the 5 published programs, so dev equals production.

Why not: A filter on data/published.json removes the local review of a new crawl before publish. It adds a check, it does not concentrate one. A product owner must decide this.
